## 一、统一规则

| 任务/费用情况 | 结算责任 | 处理 |
| --- | --- | --- |
| 成功且费用明确 | 自动 | 默认按已确认的上游净成本 ×2 结算；适用订单创建时保存的售价规则 |
| 失败且有明确上游扣费凭据 | 管理员 | 核对后按未退款的上游实际成本 ×1 收取，不加价 |
| 失败但扣费不明确 | 管理员 | 进入待核对；可继续核对、确认免单/退款，不能把报价或冻结额度直接认作已扣成本 |
| 生成成功/失败结果未知 | 管理员 | 进入待核对；结合任务记录、供应商答复或交付证据判定财务处理，不自动重新生成 |
| 成功但费用不明确 | 管理员 | 进入待核对；不因为有结果就猜测实际成本 |
| 上游后续退款 | 系统记账；异常由管理员复核 | 基于可信退款凭据追加客户退款流水及邮件通知，不删除原记录 |

管理员可以依据上游网页账单、导出明细、供应商任务级确认等可审计材料手工核对，并不强制要求上游必须提供自动账单 API。没有自动凭据的线路可采用人工审核；缺少凭据不是授权系统猜测成本。

**已确认（2026-10-09）：**Flare 成功售价保留 **¥0.10/张**，不改为成本 ×2。按验证后的实际成功图片数量计算，不能将参考图数量作为收费张数。失败/结果未知仍进入统一人工核对流程；已确认且未退款的失败成本按 ×1，且不得突破客户接受的报价上限。固定价成功不以取得上游成本为结算前提，但必须有明确的成功交付及图片数量。

## 二、内部审核与客户可见范围

“后台黑箱”指审核操作、供应商身份、进价、凭据和内部备注只对授权管理员可见，不代表可以隐蔽扣费。

- 客户可见：订单编号、生成状态、结算状态、待核对/预留金额、最终消费、退款金额、余额变动、简明处理说明。
- 管理员可见：上游账号与任务映射、渠道、订单报价快照、积分换算、成本、已退款成本、证据附件、操作人和审核历史。
- 审核后的收费、差额退款、后续退款须有客户账单记录；发送结算/退款邮件，不向邮件或客户接口泄露上游 Key、成本明细、凭据附件或内部备注。
- 新规则需在客户使用前明确告知；只适用于启用该规则后创建的订单，不追溯改变旧订单收费方式。

## 三、金额与快照

订单创建时保存：规则版本、售价模式、客户接受的报价上限、上游报价、计费单位、积分兑人民币比例、数量/时长/清晰度、所属账户与令牌、路由与上游任务映射。

以人民币最小记账单位使用整数或定点数计算，不用浮点累计。任务成本只接受同一上游账号、同一任务的已确认扣费，减去其已确认退款；不能拿当前目录价覆盖历史快照。金额不可为负，退款不可超过该单客户净实付。

成功默认 ×2，失败 ×1；报价上限为客户授权边界，管理员也不能通过后台核对自动突破。超额成本单列异常，另行处理，不静默补扣或制造负余额。管理员可选择降低收费或免单，必须记录原因。

后续退款规则已确认：失败成本透传单随净上游成本变化按 ×1 退差额；成功倍价单按原 ×2 规则重算目标金额。Flare 固定成功售价单由管理员填写客户退款金额，累计不超过该单实付。所有退款均需与原任务关联的凭据；不把任意上游账号返利当作某个客户任务退款。

## 四、财务状态独立于生成状态

生成状态仅表示 queued/running/succeeded/failed/unknown；财务状态独立保存：预留、待核对、已结算、部分退款、全额退款。

现有系统的“提交时预扣并累计消费”不能直接冒充真正的冻结余额。施工时需明确区分可用余额、预留金额和已结算消费，或在兼容现有预扣账本时提供明确状态与差额流水；避免把待核对金额同时算作可用与已消费。

查询超时、断网、空结果、进度为零都不能直接判定任务失败。待核对期间停止自动创建重试，可继续只读查询。管理员确认财务处理不得伪造上游生成成功状态；后来取得真实终态时，若与人工处理冲突，转人工复核，不覆盖已结算记录或重复扣费。

待核对处理方式已确认：**仅人工处理，到期提醒管理员**。以进入待核对后 24 小时为首个提醒时间，未处理则每天提醒；不因超时自动收费、退款或释放预留。客户必须看到预留金额与待核对状态；客服可向管理员升级，不能将预留冒充最终消费。提醒不替代人工处理责任。

## 五、管理员审核页

列表筛选：供应商/线路、生成状态、待核对原因、预留金额、等待时长、审核人。

详情区：订单快照、本站与上游任务编号、已有账本事件、成本/退款凭据、客户对外处理说明。凭据仅上传至私有存储，按权限签名读取，不使用公开媒体链接。

审核动作：

1. 补充证据并继续待核对。
2. 确认成功与费用，按该订单的售价规则结算。
3. 确认失败但上游有净扣费，按 ×1 成本结算。
4. 确认无需收费/免单，释放预留或全额退款。
5. 登记后续上游退款，预览并提交客户差额退款。

提交前展示目标费用、已经结算金额、此次补扣/退还金额及客户最终余额；要求填写原因和证据来源，不能只提供任意金额输入框直接写余额。

## 六、安全、并发和通知

- 使用后端审核权限校验，不只隐藏菜单；首期仅 piknoadmin 可操作。敏感财务动作按现有安全校验机制二次确认。
- 每个审核命令包含订单版本与唯一操作 ID；同一任务的自动结算、人工审核、上游退款都进入同一结算入口。
- 数据库事务内校验旧版本、锁定相关记录、计算目标金额与差额，原子更新客户余额、预留、令牌额度及消费/退款流水。重复提交只返回既有结果；过期页面或并发审核拒绝覆盖。
- 账本和审核历史只追加，不通过删除日志掩盖调整。操作人、原因、证据引用、前后金额与时间可追溯。
- 财务事务提交后通过 outbox 去重发送邮件；邮件失败不回滚已完成账务，也不能造成重复扣费。
- 不自动调用供应商退款接口或重新生成；这两项是独立业务动作。

## 七、施工顺序与验收门槛

1. 补齐订单财务状态、报价/规则快照、审核记录、账本差额和通知事件模型。
2. 建立统一结算入口，先以模拟回执验证成功 ×2、失败 ×1、未知待核对、免单、后续退款、金额上限。
3. 接入管理员审核页与客户状态/账单展示，执行普通客户越权检查。
4. 测试重复与乱序回调、同时审核、令牌已删除/额度不足、进程重启、邮件失败重试、部分退款和历史规则兼容。
5. 在隔离环境覆盖所有供应商适配器；再做生产灰度验收与回滚演练，最后逐条开放渠道。

通过之前维持生产原有配置；本文件不代表统一账务模块已上线。
