## 完整请求计量仍是上线关卡

- [分词 API](https://docs.volcengine.com/docs/ark/tokenization-api?lang=zh) 接受 model 与 text，不提供完整 Responses 消息、instructions 和角色模板的计量合同；[官方文本生成指南](https://docs.volcengine.com/docs/ark/text-generation?lang=zh) 将该工具用于估算，实际用量看 usage。
- [Messages 请求计数](https://docs.volcengine.com/docs/ark/messages-count-tokens-api?lang=zh) 接受 system／messages，但属于另一调用协议，并说明实际用量以真实请求为准。本次未找到其结果等于或覆盖 Responses 输入用量的官方保证。
- 因此不能以“字符数除以4”、不匹配的 tokenizer 或文本计数加经验常数，替代受预算约束的完整输入上界。生产计数器保持未绑定，不修改 enabled／verified 开关。

建议向方舟技术支持提交以下最小问题（无需提供真实 Key 或私有提示词）：

> 使用 260915 的 Responses 纯文字接口，input 含多轮 user／assistant 文本及 instructions，store=false、不使用工具或缓存链。请确认：如何在推理前获取包含全部消息模板与系统开销的输入 token 数或严格保守上界？Messages count_tokens 是否能用于该 Responses 请求，保证条件是什么？分词／计数接口是否收费？能否在服务端强制限制单请求总输入，以及输出上限是否完整包含思考 tokens？

## 对“tokenization加20即可靠上界”补充资料的复核

用户随后提供了文本分词加固定模板裕量、统一256K窗口、默认截历史和仅模型级累计限额等说明。以下为公开官方资料核对结果，不把该说明末尾的示例代码或询问当作新的实施授权：

1. **固定版本窗口不能合并。** [官方模型列表](https://docs.volcengine.com/docs/ark/model-list?lang=zh) 仍区分260915的1024k窗口与260628的256k窗口。用户引用的 `/docs/82379/2549861` 目前重定向到 [Seed-Evolving](https://docs.volcengine.com/docs/ark/latest-model?lang=zh)，该页也列1024k；它不是固定旧版2.1-pro一律256K的依据。候选中的保守路线门槛不是对“k”精确计费单位的另行认定。
2. **固定裕量只是估算，不能签成已证明的计量上界。** `+20`、单条约4～6 tokens、增加10%～20%均未给出对两个版本全部允许请求的最大模板开销保证。对输入文本或其JSON序列化分词也不等于对模型实际消息模板分词。可用于估算提示或辅助拒绝筛查，不据此绑定当前生产输入计数器；当前仍不开放多模态与工具。
3. **未查到“Responses默认丢最早历史”的当前方舟合同。** [上下文管理](https://docs.volcengine.com/docs/ark/context-management?lang=zh) 区分输入超长报错和输出触达长度停止，其示例明确将超过最大输入长度的输入判为报错；不能用 Chat 的 `finish_reason=length` 推断输入先被静默裁剪。也不把其他厂商的 `truncation` 默认值套入方舟。沿用不自动裁历史、上下文不兼容仅跳过旧路线的已确认规则，不新增未经文档支持的参数。
4. **“不支持Endpoint累计用量上限”已过时。** [2026年9月产品公告](https://docs.volcengine.com/docs/ark/product-update-announcements?lang=zh) 和 [开通管理](https://docs.volcengine.com/docs/ark/activation-management?lang=zh) 现均说明支持模型级与接入点级累计用量上限。官方还说明，请求预估用量超过剩余可用额度时会失败并触发用量上限错误。该能力是新的隔离小额验收兜底候选，不等同于任意单请求输入cap，也尚不构成并发／在途绝不超出金额的证明。
5. **上限能力仍有适用条件。** 累计限额用于已开通的在线按token／按张后付费；不适用于批量，不与前缀缓存或Fast同时启用；已购买TPM保障包／模型单元时不支持。限额重设需至少间隔2小时。当前账户适用性、最小粒度、输入与输出扣减口径、在途／并发超用边界以及具体错误的零执行零费用语义，仍需核实。未经用户另行授权，不修改现有模型或接入点限额，以免暂停其他业务。
6. **客户端不是计费信任边界。** 预校验与预算授权必须在PIKNO受信服务端执行，客户端提示只是辅助。输出上限应由已确认单次预算及服务端配置约束，不按“窗口剩余全部给输出”自动放大；该做法可能大幅增加最坏费用。实际结算仍读Responses的 `input_tokens/output_tokens`，不切成Chat字段。

本轮不再把经验裕量包装为厂家保证，也没有证明分词接口在本账户免费；通用文档调试费用提示同样不能反向证明它收费。优先核实上述新增的接入点累计上限能否支持1元内的受控验收；若最终只能使用经验估算，须先明确改变超额承担规则及风险边界，不能偷偷放宽已确认预算或把超预占差额直接扣给客户。

小额验收的条件计算：仅当能够证明三条路线**合计实际计费输入加输出** `T` 不超过20,000 tokens，且无工具、显式缓存存储等额外费用时，当前普通客户价可保证 `9I + 45O <= 45T = 900000 quota = 0.90元`；名义上游6／30对应不超过0.60元。此为条件上界，不是已经获得的账户限制或实际扣费结果；不能三条各设20,000后声称合计仍为0.90元。

下一步应先取得用量上限区域的非秘密设置证据：单位与最小值、三条路线当前限额及其他在途调用；同时确认预估偏差和并发受理是否允许超过额度、Responses思考用量是否完整覆盖。只读核验不点保存、不暂停接入点；在取得保证及另行配置授权前，不用常量替代生产计数器。用量上限错误 `SetLimitExceeded` 也不自动加入零执行换线白名单，仍需匹配的零生成、零费用证据，不能只看429。

补充链接适用性：用户引用的 `/docs/6448/2210221` 当前重定向到另一产品的 `Intelligentprocessing/ChatAPI-2`，不能作为方舟Responses完整输入模板计量依据。本次未找到方舟Responses的 `truncation` 参数合同，不据其他兼容协议添加该字段。

仅更新本内部记录，没有修改生产计数器、收费规则、输出上限、限额、Secrets或线路，没有部署或发起真实推理。
